# Decision backlog

This is the intake queue for project and architectural questions. `Stated
direction` means the design session expressed a strong preference; it does not
mean an ADR has been accepted. Accepted project-scope decisions may be recorded
in the charter or scope document; accepted architectural decisions require an
ADR.

This backlog owns question and decision state. The
[work register](work-register.md) provides the aggregate policy, mechanism,
evidence, implementation, and phase-gate view; plans and issues must not turn
this backlog into a duplicate task tracker.

A single day's work produced four failures of one species -- a task rename leaving stale references across six files, proposal-to-accepted status surviving in four places, the same status duplicated across a plan table, the current context, and the work register, and an acceptance existing only as a sentence an agent typed. None was a reasoning error; all were referential integrity or duplicated state. **The acceptance case is the serious one**: `AGENTS.md` forbids agents from accepting decisions, and that rule is currently enforced by agent good behaviour alone, with no structural difference between a real approval and a fabricated one. The 285 passing directories were pruned 2026-08-15 and the 28 failing ones kept, which is a hand fix of exactly the kind this question exists over. | S-005 | What threats and trust assertions govern boot and runtime? | [Boot-to-root and role objectives accepted; remaining threat model in review](reviews/0005-role-security-and-availability-objectives.md). **Open sub-question raised by PLN-0002-06, 2026-08-14: an untrusted `/usr` verity signer does not stop the boot, by upstream design.** Measured across both enrollment arms. The kernel does refuse the signature -- `device-mapper: reload ioctl failed: Required key not available` -- but `systemd-veritysetup` then retries without it, succeeds, and reports the unit Finished (`veritysetup.c:437-443`, unconditional). `systemd.image_policy=usr=signed` does not reach this: it is a structural predicate satisfied by both arms, evaluated after `/usr` is mounted, and non-fatal. The outcome is not discarded, it is measured -- `signed_activation` feeds `pcrextend_verity_now()`, so a signed activation and an unsigned fallback extend different PCR values. So upstream's enforcement point is the **unseal**, not the mount, and a NeutrinOS that wants a bad signer to fail closed at boot must either add that itself or accept sealing as the mechanism. PLN-0002 lists TPM policy and unlock behaviour as out of scope, so this is recorded rather than answered. See the [artifact parameter declaration](artifact-parameter-declaration.md) | S-001 |
