# Repository hygiene contract

Drafted for PRE-016. Not accepted; the owner accepts or rejects it, and the
numeric bounds below are proposals rather than decisions. The document layout
and authority table in [docs README](../README.md) remain the source for
documentation structure; this contract governs the repository around them.

## Top-level layout

The tracked top level is small and closed. Each entry has one owner and one
purpose:

| Path | Owns | Lifecycle |
| --- | --- | --- |
| `AGENTS.md` | Canonical tool-neutral agent instructions | PRE-013 |
| `CLAUDE.md` | Thin Claude adapter; imports `AGENTS.md` | PRE-013 |
| `docs/` | The entire design and project record | `docs/README.md` |
| `tools/` | Repository tooling that is not NeutrinOS source | PRE-015 |
| `mise.toml`, `mise.lock` | Toolchain and Linux-x64 lock | PRE-015 |
| `pyproject.toml`, `uv.lock` | Validation engine deps and lock | PRE-015 |
| `.github/` | Forge configuration | PRE-017 |

A new top-level entry requires a named owner and lifecycle in this table.
Absent that, it belongs under an existing directory. `tools/` holds repository
tooling only; NeutrinOS source is prohibited before G1 and will not live there
when authorized.

## Naming, identifiers, and formatting

- Follow [naming](naming.md) for every project-name form.
- Stable ID families are `PLN-nnnn`, `PRE-nnn`, `ADR-nnnn`, `DES-nnnn`,
  `PR-nnnn`, `EX-nnnn`, `W-nnn`, decision-backlog `P/S/L/C-nnn`, and test IDs
  of the form `T<level>-<AREA>-nnn`. IDs are allocated in sequence, never
  reused, and never renumbered once committed.
- A file that carries an ID is named `<id-number>-<kebab-subject>.md`.
- Documents with a lifecycle carry frontmatter with at least `status` and
  `last_updated`. Policy documents also name their governing plan or criterion.
- Markdown wraps at 79 columns. Internal links are repository-relative and are
  checked by `T0-DOC-002`; whitespace is checked by `T0-DOC-001`.

## Generated and committed content

Committed generated content is limited to dependency and toolchain locks:
`mise.lock` and `uv.lock`. Both carry a generator marker, are regenerated by
the documented bootstrap and lock commands, and are reviewed as acquisition
changes rather than as incidental churn.

Any future generated or golden output must record, next to it, what produced
it and the exact command that regenerates it. Generated content whose
provenance is not recorded may not be committed.

## Ignored local state

The following are local state and must never be tracked: virtual environments
and installed packages, validation run directories and retained logs, build
output, VM disks, firmware and vTPM state, credentials and key material,
editor and OS scratch files, and agent-local memory or session records.

Validation already keeps its run directories and cache outside the checkout,
so its evidence cannot be committed by accident.

Two current gaps, both real:

- The repository has **no tracked `.gitignore`**. `.venv/` is currently
  excluded only because uv writes `.venv/.gitignore` containing `*` — an
  artifact of a tool's behavior, not a declared repository rule. If that
  behavior changes, the virtual environment becomes committable. The tracked
  `.gitignore` is PRE-017's deliverable; the rule set above is what it must
  encode.
- `.agents/` and `.codex/` exist as empty, read-only, untracked directories.
  Git cannot see empty directories, so nothing in the repository declares or
  enforces them. They are either adapter locations that need tracked content
  or leftovers that should be removed.

## Artifact size and external retention

Proposed bounds: no tracked file above 1 MiB, and no tracked binary artifact
at all. The largest tracked file today is 69 KB, so these bind nothing
currently and exist to fail before the first image or VM disk is committed.

Images, VM disks, large evidence bundles, and retained validation output live
outside the repository. A document that depends on such an artifact records
its identity and how to reconstruct it, never the artifact itself.

## Supersession and archive

Accepted records are not rewritten to make history look cleaner. A changed
decision gets a new record that supersedes the old one, and the superseded
record keeps its ID, gains `status: superseded`, and names its successor.

Obsolete plans are retained with a terminal status rather than deleted.
Reviews are immutable once accepted; a further challenge is a new review.

## Dependencies and updates

- The toolchain is declared in `mise.toml` and locked in `mise.lock` for
  `linux-x64`; validation dependencies are declared in `pyproject.toml` and
  locked with hashes in `uv.lock`.
- Nothing is vendored. A vendoring proposal requires a recorded decision.
- Lock changes are acquisition changes: they are reviewed deliberately, never
  as drive-by updates, and a lock bump that changes tool versions requires the
  affected boundary claims to be re-checked.
- Dependency and lock ownership sits with the owner; agents propose.

## Clean-clone check

PRE-016 requires an automated check that a clean clone can run the documented
fast validation without undeclared local state. `T5-VAL-003` implements it in
the complete profile: the fast profile must stay fast, and registering the
check there would make that profile clone and re-run itself.

The check clones committed `HEAD` into a temporary directory, builds the
clone's declared environment offline from `uv.lock`, runs the clone's fast
profile, and asserts the clone is unmodified afterward. It never writes to the
operator checkout and never reaches the network.

Two bounded limitations, both deliberate:

- It requires the declared uv cache to already hold the locked packages.
  Canonical validation is offline, so acquisition cannot happen inside a test.
  A cold cache fails the check with that stated reason rather than silently
  passing or downloading.
- It drives the clone through the clone's committed runner rather than through
  `mise run`. The runner enforces a strict environment allowlist, and the mise
  configuration isolation the probe needs cannot cross it without widening
  that allowlist, which is a reviewed boundary. Mise task dispatch in a clean
  clone is therefore not covered here; `T5-VAL-002` covers dispatch under
  isolation, and closing the gap would require an owner decision on the
  allowlist.
