# Risk register

| ID | Risk | Impact | Initial response |
| --- | --- | --- | --- |
| R-001 | The project recreates an existing atomic distribution with less maintenance capacity. | Critical | Establish a differentiating invariant and perform adopt/build/borrow comparisons first. |
| R-002 | Rolling back the OS leaves incompatible mutable state. | Critical | Define state ownership, schemas, and migration compatibility before update implementation. |
| R-003 | Signing-key loss or compromise makes machines unrecoverable or untrustworthy. | Critical | Enforce accepted DES-0004 and ADR-0002; exercise authority loss through EX-0001, promotion substitution through EX-0002, and recovery abuse through EX-0003 before creating production keys. |
| R-004 | Package-input churn exceeds available security-maintenance capacity. | High | Compare release models and define patch/rebuild service objectives. |
| R-005 | Hardware breadth prevents reliable qualification. | High | Publish a narrow initial hardware matrix and expand only with tests. |
| R-006 | Role abstraction becomes either duplication or an overly clever configuration language. | High | Model two substantially different roles before fixing the abstraction. |
| R-007 | Rootless containers conflict with identity or home-directory choices. | High | Treat UID, sub-ID, idmapped mount, and bind-mount behavior as a gated design. |
| R-008 | Security mechanisms accumulate without a coherent threat model. | High | Require every mechanism to map to assets, attackers, and recovery behavior. |
| R-009 | Custom kernels create an unsustainable support matrix. | Medium | Begin with a generic reference kernel and require measured benefit for variants. |
| R-010 | Desktop details distract from the end-to-end release lifecycle. | Medium | Defer component selection until the system model and reference role are chosen. |
| R-011 | The spoken name and lowercase identifier collide with existing software companies, including one using OS language. | Low for the personal phase | Use the distinctive `NeutrinOS` display style, retain existing repository identifiers, and review naming before any public distribution or third-party namespace commitment. |
| R-012 | The selected substrate's production backend cannot provide the accepted boot trust or automatic recovery model. | Critical | Accept trust requirements before the substrate ADR and run symmetric lifecycle spikes against production-supported configurations. |
| R-013 | Recovery becomes an alternate privileged boot path that bypasses data, identity, platform, or normal-release controls. | Critical | Enforce the EX-0003 capability transitions; physically test activation, unlock, hostile-state handling, independent evidence, signer replacement, and router out-of-band isolation before production enrollment. |
| R-014 | Separately transferred boot, root, extension, or configuration resources can form a partial or hybrid deployment that was never jointly qualified. | Critical | Require the DES-0001 complete deployment-set identity, inert staging, one selection boundary, boot-time binding, and power-loss injection on each substrate. |
| R-015 | Exact machine variants and qualification create unsustainable build, storage, and test growth. | High | Apply the EX-0005 factoring and evidence-reuse boundaries; measure workstation and router variants and compare flattened rebuilds with separately bound immutable configuration artifacts. |
| R-016 | An exact immutable base is mistaken for proof that mutable platform, administrator, user, or workload inputs are qualified or uncompromised. | Critical | Enforce the EX-0004 ownership and status split; inventory actual loaders and persistent executable inputs; test rollback and recovery with hostile mutable state. |
| R-017 | Separately updated UKI, root, Verity, and configuration artifacts form a locally valid but never-qualified hybrid. | Critical | Enforce DES-0006 exact boot binding, install the entry point last, and run pairwise substitution plus power-loss tests across every storage and selection transition. |
| R-018 | TPM policy, recovery keys, or LUKS metadata loss either exposes protected state or makes it permanently unavailable. | Critical | Keep hardware-bound and independent recovery paths, separate their custody, back up headers, rotate by add-test-remove, and exercise firmware, TPM, mainboard, and key-loss recovery. |
| R-019 | Fixed deployment slots and uncontrolled state growth exhaust capacity, especially on the router's 16 GB system disk. | Critical | Measure literal artifacts, enforce DES-0006 capacity reserves, compare router disk layouts, and test full-storage behavior before accepting partition sizes. |
| R-020 | A mutable repository URL, package version, or archive date is mistaken for the identity of the package inputs actually resolved and built. | Critical | Require the DES-0007 package input snapshot, retain exact metadata and package bytes, and reject mixed or silently re-resolved closures. |
| R-021 | A valid but old signed package snapshot is reported as current after a security advisory or upstream end of life. | Critical | Keep snapshot identity, signature validity, vulnerability applicability, upstream support, and NeutrinOS currentness separate; test old-valid-snapshot status transitions. |
| R-022 | A third-party repository, recipe, binary, or package install script compromises the build, release key, or fleet secrets. | Critical | Use finite declared intake, isolate executable package inputs from signing and machine authorities, deny undeclared network access, and exercise a hostile package. |
| R-023 | The selected ecosystem forces either rolling qualification churn or a private packaging and branch-migration burden that one maintainer cannot sustain. | Critical | Complete EX-0009 with literal Fedora and Arch closures, security-refresh and major-transition scenarios, and measured owner time before accepting the ecosystem ADR. |
| R-024 | Schema-valid or signed provenance is mistaken for proof that a builder, inputs, or output are trustworthy. | Critical | Separate record identity, producer authentication, expectation verification, SLSA assessment, qualification, and independent reproduction; inject false and incomplete attestations under DES-0008. |
| R-025 | An apparently complete SBOM omits vendored, generated, statically linked, initrd, firmware, plugin, script, or other non-package executable content. | Critical | Require subject-bound coverage by component class, retain native package and artifact identity, and expose opaque/unparsed content as SBOM coverage gaps. |
| R-026 | Vulnerability matching misclassifies distro backports, forks, build configuration, aliases, or package identity, causing false reassurance or wasted emergency work. | Critical | Preserve native/source identities and raw advisory records, make matching evidence explicit, retain conflicts and unknowns, and exercise distro-backport and missing-advisory cases. |
| R-027 | A copied, stale, or malicious VEX claim suppresses a real vulnerability. | Critical | Bind every assessment to exact deployment/component/vulnerability/configuration, authority, evidence, expiry, and action; never delete the raw finding and test contradiction/reopening. |
| R-028 | Build replay, same-builder output, partial-payload comparison, or deterministic metadata is mislabeled as independent reproducibility. | High | Use DES-0008's per-artifact vocabulary, preserve comparison boundaries/diffs, and prohibit broader claims than the literal compared subjects support. |
| R-029 | Evidence identity cycles, schema churn, garbage collection, service loss, or over-retention make historical release decisions unverifiable or leak sensitive data. | Critical | Use acyclic content-identified records, pin formats and validators, derive migrations without rewriting history, apply owner-specific sensitivity/retention, and exercise offline loss/full-storage recovery. |
| R-030 | A rollout service, channel, group, or reboot coordinator becomes an implicit release authority or bypasses local eligibility. | Critical | Enforce DES-0009 action and authority separation; inject valid but unauthorized, incompatible, withdrawn, and wrong-subject offers before selecting a mechanism. |
| R-031 | Small or heterogeneous cohorts create percentage theater: one unrelated success is used to justify a high-consequence role. | Critical | Freeze exact membership, state each cohort's evidence boundary, use role-specific representative VMs, and require an explicit attended singleton policy where no valid canary exists. |
| R-032 | Pause, withdrawal, offline caching, replay, or controller restore produces conflicting decisions or a larger in-flight blast radius than operators can see. | Critical | Use append-only ordered revisions and bounded action grants; display in-flight transitions and exercise partitions, stale clocks, replay, split brain, and restore through EX-0011. |
| R-033 | Rollout automation and private telemetry cost more to operate or disclose more fleet data than the personal fleet justifies. | High | Prove the policy first with minimal static records and attended execution; measure services, credentials, data, storage, upgrades, and owner time against Nebraska and Cincinnati-derived alternatives. |
| R-034 | A bootstrap hint, copied voucher, installer display, metadata service, or hardware identifier binds an attacker or wrong device to a privileged machine record. | Critical | Require scoped single-use authority effect, fresh proof of possession, independent request confirmation, explicit approval/epoch, and hostile bootstrap plus race tests in EX-0012. |
| R-035 | Installer bugs, compromise, ambiguous disk selection, or interrupted storage mutation destroys existing workstation/router data or creates a bootable hybrid. | Critical | Authenticate the installer, require stable target-bound preflight and verified backups, install the final entry point last, and inject remapping and power loss across every phase. |
| R-036 | Ignition, cloud-init, installer credentials, or first-boot hooks become a second normal configuration system or replay after enrollment. | Critical | Generate a bounded allowlisted handoff, reject release-owned policy injection, join completion to current binding/epoch, neutralize inputs, and test metadata/cache/seed replay. |
| R-037 | Backup, disk clone, VM clone, reinstall, or OS rollback resurrects a revoked or duplicated machine identity. | Critical | Give identity an independent epoch/revocation lifecycle, treat restore as conditional, detect duplicate use, and exercise clone, old-backup, rotation, and re-enrollment cases. |
| R-038 | Platform-key, TPM/LUKS, enrollment, and recovery ceremonies interact in an order that strands the machine or silently weakens protection. | Critical | Keep authorities separate, use add-test-remove transitions, preserve independent recovery, back up metadata, and physically exercise firmware reset, TPM clear, key loss, and return paths. |
| R-039 | A credential, encrypted file, secret-service template, or metadata response becomes an unqualified second configuration and code channel. | Critical | Bind every value to an identity-bound credential contract with bounded semantics; reject code and privileged policy smuggling through every adapter in EX-0013. |
| R-040 | A shared broker, decryption key, recipient, store, or issuer turns one machine or service compromise into fleet-wide secret disclosure. | Critical | Use exact machine/epoch/consumer grants, separate secret classes and owners, prohibit undeclared fleet-wide capabilities, and traverse each holder's dependents before mechanism selection. |
| R-041 | TPM/host-bound credential encryption is mistaken for backup, making hardware or `/var` loss unrecoverable. | Critical | Classify every value as reissuable or independently recoverable and exercise TPM clear, host-key loss, disk/mainboard replacement, and old-backup restore with literal encryption modes. |
| R-042 | Credential rotation causes outage, split-brain authentication, or indefinite old-key acceptance because retrieval is mistaken for consumer adoption. | Critical | Use explicit prepare/overlap/activate/verify/retire transactions and test native renewal plus restart/drain paths with interruption and peer-state mismatch. |
| R-043 | An offline high-availability machine continues using a revoked credential longer than operators or peers understand. | Critical | Declare maximum cache validity and clock policy per contract, expose authority knowledge time and unseen-revocation risk, and exercise loss/reconnect around issue, rotation, and revocation. |
| R-044 | Reinstall, restore, or host movement binds durable numeric-owned state to a different human, service, or subordinate namespace identity. | Critical | Use authoritative allocation manifests, fail collisions, separate numeric from authenticated identity, and exercise same/different-map raw restores before selecting UID/sub-ID policy. |
| R-045 | A UID/GID or subordinate-range migration misses ACLs, xattrs, snapshots, archives, backups, or container stores and later range reuse exposes forgotten state. | Critical | Treat changes as interruption-safe state migrations, inventory retained dependencies, prohibit blind recursive chown, and tombstone old ranges until destruction evidence exists. |
| R-046 | Rootless or `keep-id` is mistaken for complete isolation while bind mounts, groups, devices, sockets, credentials, or concurrent namespace modes retain dangerous access. | Critical | Declare exact maps and attachments per workload and test hostile access plus Podman/Docker mapping concurrency rather than inferring safety from rootless execution. |
| R-047 | Idmapped mounts or systemd-homed appear compatible in documentation but fail the actual filesystem, rootless-store, source-bind, session, backup, or recovery workflow. | Critical | Keep the classic fixed-account baseline and require EX-0014 literal Btrfs/ext4, Podman/Docker, homed, session, collision, restore, and recovery evidence before adoption. |
| R-048 | Fixed service identities collide across Fedora, Arch, project packages, restored state, or external protocols, while dynamic identities make offline recovery ambiguous. | High | Inventory package/service allocations, prefer `DynamicUser=` only for fully mediated state, and register fixed IDs only with demonstrated durable semantics and restore tests. |
