# System requirements

These requirements are extracted from the design session and subsequent
research. The status of each requirement is tracked independently. `Accepted`
means the requirement is normative project policy, not that a design has yet
satisfied it. `Superseded` preserves an earlier requirement whose normative
replacement is identified by its acceptance review.

| ID | Status | Requirement | Acceptance evidence |
| --- | --- | --- | --- |
| SYS-001 | Accepted | A release must be traceable to source revision, pinned inputs, build configuration, and test results. | Deployment manifest, release authorization, and provenance verification. |
| SYS-002 | Accepted | Qualification must boot and test the exact deployment identity and complete deployment closure that are offered for deployment. | Deployment manifest, deployment closure, artifact digests, and boot-test record. |
| SYS-003 | Accepted | A failed or interrupted deployment-lifecycle transition must leave the prior valid selection intact, select another eligible retained deployment, or preserve a documented, testable path to deliberate recovery. | Failure-injection test matrix for every lifecycle transition. |
| SYS-004 | Superseded | The system must identify the owners and lifecycles of OS, machine, administrator, user, and workload state. | Superseded by SYS-019. |
| SYS-005 | Accepted | Role specialization must retain common deployment identity, release, update, status, and recovery semantics without requiring identical artifact shapes. | Cross-role architecture trace. |
| SYS-006 | Superseded | Machine and role configuration must be reviewable in version control. | Superseded by SYS-014 through SYS-018. |
| SYS-007 | Superseded | Security mechanisms must state the assets, attackers, guarantees, and recovery behavior they address. | Superseded by SYS-027. |
| SYS-008 | Accepted | The running machine must expose its exact booted deployment identity and the evidence needed to correlate it with its deployment manifest, release authorization, and qualification record. | On-machine identity and evidence-correlation test. |
| SYS-009 | Superseded | Mutable-state changes must not silently make the advertised rollback path unusable. | Superseded by SYS-021 through SYS-023. |
| SYS-010 | Accepted | Every supported role must define externally observable health and acceptance criteria. | Role qualification specification. |
| SYS-011 | Superseded | The system must distinguish the current qualified release from stale, pinned, locally modified, and unsupported deployments. | Superseded by SYS-031. |
| SYS-012 | Accepted | An emergency release must retain minimum provenance, content integrity, literal-artifact boot, changed-behavior qualification, and an applicable fallback, rollback, or maintenance-recovery exercise; skipped normal checks and reduced claims must remain explicit. | Emergency release evidence, exercised return path, and documented skipped checks and reduced claims. |
| SYS-013 | Accepted | Every deployed software component must expose who owns its vulnerability monitoring and update lifecycle. | Cross-component maintenance ownership inventory. |
| SYS-014 | Accepted | Normal machine and role intent must be expressible as bounded declarative data or upstream-native configuration; understanding it must not require evaluating a general-purpose programming language. | Representative workstation and router configurations reviewed without composition-engine knowledge. |
| SYS-015 | Accepted | A missing project convenience schema must not prevent use of a supported upstream setting; native configuration and explicit pass-through inputs must remain attributable and testable. | Exercise an unmodeled upstream setting through the documented native-input path and trace it into qualification evidence. |
| SYS-016 | Accepted | Configuration composition must have deterministic precedence and expose the fully resolved inputs and generated native configuration used for an artifact. | Composition inspection and conflicting-override tests. |
| SYS-017 | Accepted | Deployment must select a previously built and qualified artifact rather than evaluate arbitrary machine configuration or reconstruct an equivalent OS on the machine. | Deployment trace joined to the qualified artifact identity. |
| SYS-018 | Accepted | A configuration or deployment failure must identify the responsible input, configuration scope, generated output, and lifecycle stage. | Negative tests for schema, composition, generation, staging, selection, boot, and health-assessment failures. |
| SYS-019 | Accepted | Every persistent state item or namespace must identify its lifecycle owner, authority, schema or format, compatibility, migration, backup, recovery, and reset behavior. | State-contract inventory traced to workstation and router acceptance tests. |
| SYS-020 | Accepted | The normal effective `/etc` must be reconstructible from identified inputs; every persistent exception and administrator override must be explicit, attributable, inspectable, and reflected in machine support status. | Clean reconstruction, persistent-exception inventory, and locally-modified status tests. |
| SYS-021 | Accepted | Before a deployment becomes eligible for selection, its release must declare and verify read/write compatibility with the machine's state schema and every deployment offered as an automatic fallback candidate. | Compatibility matrix and candidate/fallback tests against post-update state. |
| SYS-022 | Accepted | A state migration must be idempotent or detect completion and must define its interruption, retry, reversal, checkpoint, and recovery behavior. | Failure injection at each migration boundary. |
| SYS-023 | Accepted | A release with a forward-only destructive migration must expose an explicit commit barrier and must not advertise normal automatic fallback after crossing it. | Maintenance-release exercise with backup verification and recovery evidence. |
| SYS-024 | Accepted | Reinstall, reprovision, and recovery must preserve only state selected by an ownership-aware preservation manifest rather than an undifferentiated mutable filesystem. | Recovery tests with mixed machine, user, workload, cache, secret, and diagnostic state. |
| SYS-025 | Accepted | Machine identity, enrollment records, and secrets must have lifecycles independent of OS rollback, including rotation, revocation, regeneration or restore, and destruction. | Re-enrollment, revocation, rollback, and factory-reset tests. |
| SYS-026 | Accepted | Failed-update diagnostics must remain available through rollback or recovery subject to explicit sensitivity, retention, and storage limits. | Failure evidence retrieval, redaction, rotation, and full-storage tests on each role. |
| SYS-027 | Accepted | Every security claim must identify its protected assets, attacker capabilities, trust assumptions, guarantees, non-guarantees, and compromise-recovery behavior for each applicable role. | Threat-to-control trace reviewed against workstation and router scenarios. |
| SYS-028 | Accepted | A deployable release authorization must bind the exact deployment identity, qualification record, authorization scope, configuration identity or compatibility, and freshness policy independently of transport location or mutable discovery name. | Registry and metadata substitution tests against a release authorization joined to its deployment manifest and qualification record. |
| SYS-029 | Accepted | A candidate must be fully staged and eligible before it can replace or outrank the currently selected deployment; failed or interrupted acquisition, verification, or eligibility evaluation must leave that selection intact. | Corruption, substitution, interruption, policy-gate, and partial-staging tests. |
| SYS-030 | Accepted | Normal boot on a production physical role must authenticate, from the configured platform trust anchor, every release-owned boot artifact and the release-owned root content before executing or mounting it as normal release-owned content. | Tamper tests for bootloader, kernel, initrd, command line or equivalent policy, and immutable root. |
| SYS-031 | Accepted | Machine status must report deployment identity, authorization, boot integrity verification, provenance, qualification, freshness, currentness, compatibility, health, blessing, support, and local modification as distinct properties. | Status-schema tests covering every independent combination relevant to operations and recovery. |
| SYS-032 | Accepted | Every signing, enrollment, platform, machine, recovery, and data-encryption authority must define scope, storage, delegation, rotation, revocation, audit, loss, compromise, backup or regeneration, and destruction behavior. | Exercised authority inventory and loss/rotation/revocation runbook. |
| SYS-033 | Accepted | Recovery authorization must remain independently usable after loss or compromise of the normal release signer and must not silently authorize a normal fleet release. | Offline recovery after signer loss and compromise. |
| SYS-034 | Accepted | Each role must declare the data protected against powered-off device loss and an unlock/recovery model consistent with its unattended availability requirements. | Workstation theft-confidentiality test and router unattended reboot/recovery test. |
| SYS-035 | Accepted | Compromise recovery must treat mutable executable state, machine identity, administrator overrides, user state, and workload state as potentially hostile and support owner-aware quarantine, selective restore, re-enrollment, or destruction. | Compromise-recovery exercise distinct from ordinary OS rollback. |
| SYS-036 | Accepted | Cryptographic authorization must not substitute for provenance or qualification; promotion must verify that the authorized artifact identities are the literal qualified outputs. | Negative test signing an attributable but unqualified rebuild. |
| SYS-037 | Accepted | Freshness, revocation, and downgrade policy must distinguish deployments authorized for normal use, recovery-only use, and withdrawn use without making declared offline recovery impossible. | Offline rollback and recovery tests after expiry, withdrawal, clock failure, and authority unavailability. |
| SYS-038 | Accepted | Every trial boot must have durable bounded attempt accounting, and a deployment may be blessed only after its exact booted identity passes the applicable role-health assessment. Exhaustion must select an eligible normal fallback or stop with an attributable diagnosis; it must not enter recovery automatically. | Power-loss and repeated-failure tests before, during, and after boot assessment and blessing. |
| SYS-039 | Accepted | Blessing must apply only to one deployment identity on one machine and must not create or replace release authorization, provenance, qualification, compatibility, or fleet-wide health evidence. | Cross-machine and substituted-identity tests proving that one machine's blessing cannot authorize or qualify another deployment. |
| SYS-040 | Accepted | Retention and garbage collection must preserve the complete deployment closure and required selection metadata of every selected or booted deployment and every deployment or recovery environment with a retention reference until that reference is removed. | Shared-content reachability and interruption tests across selection, fallback, rollback, recovery, and garbage collection. |
| SYS-041 | Accepted | Once the required deployment sets, policy, and evidence are retained locally, the control path for normal boot, health-result recording, blessing, fallback, and deliberate rollback must not require a publication service, discovery service, package repository, signing environment, WAN, public DNS, or the machine's own production service path. A failed production service may fail health assessment, but it must not prevent recording that result or selecting an eligible fallback. | Offline lifecycle tests for the reference VM, workstation, and router with all named dependencies unavailable. |
| SYS-042 | Accepted | The authoritative fleet inventory must version machine records, exactly one primary role assignment per machine, platform constraints, and exact configuration-source references independently of runtime observations. | Inventory reconstruction, role-conflict, and observation-drift tests for every reference machine. |
| SYS-043 | Accepted | Platform observations and bootstrap hints must not assign a role or authorize a deployment; normal selection must join an enrolled machine identity's current machine-record binding and role assignment with a compatible platform and eligible deployment identity. | Hostile SMBIOS, metadata substitution, duplicate-record, and re-enrollment tests. |
| SYS-044 | Accepted | Configuration composition must use fixed `common < role < machine` precedence, explicit same-scope conflict and deletion rules, and policy validation after precedence resolution. | Override, tombstone, same-scope conflict, and forbidden-override tests. |
| SYS-045 | Accepted | Every deployment variant must retain an immutable composition record identifying its ordered inputs, tool identities, precedence decisions, validations, resolved configuration, rendered outputs, and declared exceptions. | Bidirectional source-to-output attribution and reproduction tests. |
| SYS-046 | Accepted | Every late-bound input must have an identity-bound contract covering ownership, source, consumer, schema, constraints, delivery or observation, failure behavior, status effect, and qualification fixtures. | Workstation and router late-bound inventories with absent, invalid, stale, and substituted-value tests. |
| SYS-047 | Accepted | Provisioning and enrollment must remain separate from normal configuration and deployment selection, and replay must not silently change role assignment, machine identity, preserved state, or selected deployment. | Interrupted provisioning, replay, reprovision, and ordinary-reboot tests. |
| SYS-048 | Accepted | Every persistent partition, volume, filesystem, subvolume, mount, image store, and reserved region must map to explicit deployment, recovery, lifecycle-metadata, state-contract, or capacity-reserve purposes; shared physical storage must not erase owner-specific lifecycle semantics. | Storage map traced bidirectionally to every deployment artifact, recovery reference, mount, and state contract on each reference role. |
| SYS-049 | Accepted | Normal release root content must be mounted read-only and authenticated against an exact identity carried or authenticated by the selected boot artifact; independently valid substituted release-owned members must fail the boot-integrity gate. | UKI, root, Verity, configuration, manifest, and slot-substitution matrix on VM and physical roles. |
| SYS-050 | Accepted | Storage and selection must preserve the complete booted deployment and capacity for one complete candidate or eligible fallback; partial staging must not consume the booted closure, expose a boot entry, or assemble a hybrid deployment. | Power-loss injection before and after every artifact, label, boot-entry, and selection transition. |
| SYS-051 | Accepted | Each role must map protected data and every relevant plaintext spill path—including swap, hibernation, crash dumps, temporary storage, diagnostics, and workload scratch data—to a declared encryption and unlock boundary. | Powered-off inspection and plaintext-canary tests for every protected state class and spill path. |
| SYS-052 | Accepted | Every encrypted volume must define and exercise routine unlock, independent recovery, metadata or header backup, enrollment, rotation, loss, compromise, restoration, and destruction behavior outside its own failure domain. | Key rotation, lost routine method, recovery-key use, header corruption/restore, disk replacement, and destruction exercises. |
| SYS-053 | Accepted | Unattended hardware-bound unlock must bind a hardware-protected secret to the accepted authenticated or measured boot policy and pass update, rollback, firmware, reset, and recovery tests; a colocated software secret must not be represented as equivalent. | Authorized/substituted UKI tests plus firmware update, Secure Boot change, TPM clear/loss, offline reboot, and recovery. |
| SYS-054 | Accepted | An independently authorized recovery environment must boot without automatically unlocking, mounting, executing, or restoring normal mutable state; each transition must be deliberate, attributable, and owner-aware. | Availability- and compromise-recovery exercises with hostile state and state initially locked. |
| SYS-055 | Accepted | Filesystem and block snapshots, reflinks, and checkpoints must remain named state-owner operations and must not imply deployment identity, independent backup, application consistency, or whole-state rollback. | Owner-specific checkpoint, interruption, restore, capacity, and OS fallback tests. |
| SYS-056 | Accepted | Every layout must reserve and enforce capacity for the booted deployment, required candidate or fallback, retained recovery, update temporaries, state migration, bounded diagnostics, and safety margin; growth and garbage collection must fail before violating those references. | Artifact-size budget, full-storage, growth, garbage-collection, diagnostic-retention, and layout-migration tests per role. |
| SYS-057 | Accepted | Every package resolution must identify the distribution, branch or release, architecture, declared repositories and precedence, trust policy, exact repository metadata, solver identity, and dependency policy; a mutable location, date, name, or version alone must not be input identity. | Repeated resolution plus mirror-mutation, metadata-substitution, repository-precedence, and solver-version tests. |
| SYS-058 | Accepted | Every build must record and retain the complete resolved binary package closure, exact package and metadata bytes, dependency reasons, verification results, and source or recipe attribution needed to reconstruct its image inputs without re-resolution from current upstream state. | Offline reconstruction with upstream unavailable, followed by bidirectional file-to-source and package-to-deployment tracing. |
| SYS-059 | Accepted | Package resolution must fail on undeclared repositories or accidental mixing of branch, repository state, architecture, or trust domain; every explicit project or third-party source must trigger a fresh whole-closure solve, attribution, and applicable qualification. | Mixed-date/branch/architecture, dependency-confusion, source-precedence, package-replacement, and third-party-addition tests. |
| SYS-060 | Accepted | Package input identity, byte availability, signature validity, source provenance, reproducibility status, vulnerability applicability, upstream support, NeutrinOS currentness, and qualification must remain distinct observable properties. | Old-valid-snapshot, new-advisory, revoked-key, unavailable-source, unreproducible-package, and qualified-vulnerable combinations. |
| SYS-061 | Accepted | Every included package and project-built component must identify its upstream branch, maintenance owner, advisory source, and end-of-life, replacement, or removal trigger; loss of upstream maintenance must become visible before it silently invalidates the current release line. | Component-owner inventory, advisory-to-deployment lookup, branch-EOL warning, stale transition, and unsupported-status tests. |
| SYS-062 | Accepted | A third-party recipe, repository, or binary must enter only as a finite declared input with source or publisher identity, license, recipe/build or explicit binary-only provenance, maintenance and vulnerability owner, isolation, qualification, and removal behavior. | Source-built and binary-only intake exercises plus repository-expansion, owner-loss, source-removal, and license-change failures. |
| SYS-063 | Accepted | Package scriptlets, triggers, macros, dependency generators, and source recipes must be treated as executable build inputs and run without release-signing private keys, fleet or machine secrets, or undeclared network access; their relevant effects and diagnostics must remain attributable. | Hostile-package tests probing network, signing and machine credentials, host paths, undeclared writes, and falsified output. |
| SYS-064 | Accepted | Changing the selected upstream branch or package universe must create a new input baseline and pass full applicable deployment and state-compatibility qualification; retained deployments from the prior branch must not imply continued upstream maintenance or a second current NeutrinOS release line. | Fedora branch or equivalent universe-transition exercise covering overlap, rollback, state compatibility, EOL, stale, and current-line status. |
| SYS-065 | Accepted | Every evidence record must bind exact subject identities, claim type, literal format and schema or predicate version, producer and tool identity, generation time, evidence dependencies, completeness and omissions, sensitivity, applicable verification policy, and its own content identity; record identity must not imply truth. | Schema/version, subject-substitution, producer-substitution, omitted-field, content-mutation, unknown-format, and claim-verification tests. |
| SYS-066 | Accepted | Build, composition, SBOM, qualification, reproduction, vulnerability, and authorization evidence must join existing subject identities through acyclic content-identified records and evidence sets; promotion must retain the exact evidence set it used, and later evidence must append or supersede claims without mutating deployment identity or historical records. | Evidence-DAG cycle detection, promotion reconstruction, post-release advisory, supersession, contradiction, and historical-verification tests. |
| SYS-067 | Accepted | Build provenance must identify exact output subjects, declared material inputs, builder and platform, build type and parameters, toolchain and environment, isolation and network/secret policy, times, completeness, and whether it was builder-generated or reconstructed; authentication and any SLSA or other assurance level must remain separately verified claims. | Complete, incomplete, false-signed, reconstructed, wrong-builder, subject-substituted, parameter-changed, and unsupported-level attestations. |
| SYS-068 | Accepted | Each deployment SBOM must bind exact deployment or artifact subjects and inventory release-owned package and non-package executable components, native and source identities, digests, relationships, and maintenance ownership; vendored, generated, opaque, unparsed, and separately owned content must be represented or declared as a coverage gap rather than silently omitted. | Package/filesystem/binary comparison covering kernel, initrd, UKI, modules, firmware, scripts, plugins, static/vendored code, opaque binaries, user software, and workload boundaries. |
| SYS-069 | Accepted | Build replay, same-builder byte equality, independent bit reproduction, semantic comparison, failure, and unassessed status must remain distinct; every result must name exact compared subjects, source/instructions/environment boundary, builder trust relation, comparison algorithm, differences or exclusions, and policy consequence. | Replay, same-builder, independent-builder, signed-versus-unsigned, excluded-field, nondeterministic, unavailable-input, and failed-comparison exercises. |
| SYS-070 | Accepted | Vulnerability processing must retain exact source records and acquisition/modification times, identifiers and aliases, source authority, component-matching method, native/source package and deployment mapping, role/configuration, severity sources, backport/fork evidence, conflicts, and unknown coverage; absence of a finding must not imply absence of vulnerabilities. | Distro-backport, fork, alias, version-range, compiled-feature, false-positive, false-negative, conflicting-source, missing-source, and no-finding cases. |
| SYS-071 | Accepted | Every applicability, exploitability, reachability, mitigation, accepted-risk, or negative VEX claim must bind the exact deployment/component/vulnerability and applicable role/configuration, issuer and authority, justification, supporting evidence, policy, time, expiry or review trigger, and required action; it must not delete the finding, imply a fix, or transfer to another subject without re-evaluation. | Valid, copied, expired, unsupported-authority, evidence-free, contradicted, configuration-changed, rebuilt-subject, and malicious VEX tests. |
| SYS-072 | Accepted | New or corrected advisory, assessment, VEX, exploit, and compromise facts must reevaluate currentness, support, eligibility, rollout, withdrawal, and recovery under a named ordering, freshness, clock, and conflict policy without changing historical deployment identity, provenance, SBOM, qualification, or authorization records; offline decisions must disclose their knowledge time and freshness limit. | Post-release advisory, concurrent/conflicting assessment, withdrawal, offline cache, stale clock, rollback, recovery-only, and service-restoration tests. |
| SYS-073 | Accepted | Evidence required for selected, staged, retained, recovery-referenced, withdrawn-but-installed, incident-held, or otherwise policy-referenced subjects must survive garbage collection and remain queryable without mutable upstream services; each evidence class must define owner, sensitivity, redaction, retention, archive, loss, and deletion behavior. | Offline bidirectional query, redaction, evidence loss, schema/tool retirement, full-storage, archive restore, garbage collection, and deletion-policy tests. |
| SYS-074 | Accepted | Compromise, revocation, or discovered misbehavior of a source, builder, attester, qualifier, normalizer, scanner, or assessment authority must identify every dependent record, deployment, release, and machine and drive explicit reverification, reassessment, withdrawal, rebuild, requalification, or accepted risk; historical records must be distrusted or superseded rather than erased. | Producer-compromise graph traversal covering shared inputs, evidence forgery, normalization corruption, scanner blind spot, key revocation, withdrawal, rebuild, and historical audit. |
| SYS-075 | Accepted | Every rollout plan and decision must bind the exact release authorization, deployment variants, promotion evidence set, authoritative inventory snapshot, policy and authority, ordering and validity, target scope, gates, and permitted actions; rollout may restrict authorized use but must not authorize a different deployment or rewrite promotion history. | Subject-, evidence-, inventory-, authority-, scope-, action-, ordering-, expiry-, and substitution tests across plan creation, advance, pause, resume, supersession, and termination. |
| SYS-076 | Accepted | Rollout cohort membership must derive from enrolled machine identity and an immutable authoritative inventory snapshot through exact materialization or a pinned deterministic selector; runtime self-labels, observations, and mutable controller state must not assign role, elevate priority, or silently change an active cohort. | Inventory-change, selector-version, cohort-reshuffle, self-label elevation, cloned-identity, missing-member, and controller-restore tests. |
| SYS-077 | Accepted | Discovery, acquisition, staging, activation permission, local selection, reboot coordination, trial boot, assessment, and blessing must remain distinct actions, and each target must independently enforce exact authorization, integrity, compatibility, freshness, and local policy; no channel, server response, rollout grant, or reboot slot may substitute for local eligibility. | Valid and malicious channel/server/grant/lease combinations at every lifecycle boundary, including inert staging and wrong-subject selection. |
| SYS-078 | Accepted | Every rollout action must bind exact current and target deployment identities and a qualified transition path covering applicable state compatibility, intermediate releases, input-baseline changes, and downgrade policy; human versions, channels, or ordering labels must not authorize an unqualified skip or transition. | Direct, intermediate, skipped, downgrade, cross-baseline, incompatible-state, and missing-source transition tests. |
| SYS-079 | Accepted | Every rollout cohort must declare exact membership, representativeness and limits, entry and exit gates, observation deadline, missing-data policy, and stop conditions; observations must bind machine, target deployment, boot, health policy, producer, and time, while success, failure, fallback, missing, stale, mismatched, excluded, pinned, and deferred outcomes remain distinct and machine-local blessing never becomes fleet qualification. | Exact-denominator tests with successful, failed, lying, unreachable, late, wrong-deployment, excluded, pinned, and fallback members plus explicit accepted-risk advancement. |
| SYS-080 | Accepted | Rollout start, advance, acquisition pause, activation pause, resume, supersession, termination, and withdrawal decisions must be authenticated, append-only, idempotent, replay-resistant, and comparable under a named epoch and ordering policy, with explicit scope and in-flight boundary; withdrawal must outrank ordinary grants and exceptions without erasing retained bytes or history. | Replay, reordering, concurrency, split-brain, stale restore, pause-race, already-selected, resume, supersession, and withdrawal-precedence tests. |
| SYS-081 | Accepted | Loss of discovery, rollout, publication, telemetry, coordination, WAN, DNS, or trustworthy time must not grant new progress or prevent the retained local lifecycle required by SYS-041; any cached decision must bind exact machine, action, source, target, epoch, and freshness, and reconnect must safely reconcile delayed, duplicated, or conflicting records. | Failure injection before and after discovery, acquisition, staging, selection, assessment, blessing, and fallback plus stale-clock, cached-grant, replay, and reconnect tests. |
| SYS-082 | Accepted | Activation and reboot must obey declared role and failure-domain availability policy for windows, inhibitors or drain behavior, concurrency, external observation, and alternate access; any reboot lease must define owner, scope, expiry, crash recovery, and reconciliation and must confer no software eligibility or authority, while singleton high-consequence roles use an explicit attended or otherwise justified policy. | Window, DST/clock, inhibitor timeout, failed drain, leaked/duplicate lease, partition, coordinator crash, shared failure-domain, and singleton-router tests. |
| SYS-083 | Accepted | Every pin or deferral must record owner, reason, exact scope, creation, expiry or review trigger, support and security consequence, and remediation; it must not override withdrawal, and healthy, pinned, stale, current, and supported must remain independent status properties. | Expired, repeatedly renewed, ownerless, withdrawn, vulnerable, offline, healthy-but-stale, and unsupported pin/deferral tests. |
| SYS-084 | Accepted | Rollout status and audit must reconstruct plans, decisions, grants, observations, exceptions, in-flight actions, and per-machine lifecycle state from attributable retained records while preserving raw substrate diagnostics; sensitive machine identity, topology, timing, failure, and exposure data must follow declared collection, access, disclosure, retention, redaction, loss, and deletion policy. | Bidirectional decision/machine queries, native-diagnostic comparison, privacy minimization, unauthorized access, redaction, retention, deletion, evidence-loss, and controller-rebuild tests. |
| SYS-085 | Accepted | Emergency rollout must bind the maintenance-policy incident class, exact affected scope, compressed or skipped gates, reduced claims, blast radius, SYS-012 minimum evidence, applicable fallback or maintenance recovery, stop overrides, approver, and follow-up obligation; overriding an automatic safety stop must require a new attributable risk decision. | Normal-versus-emergency comparison, false urgency, minimum-gate failure, skipped-cohort, simultaneous rollout, stop override, failed replacement, fallback, and follow-up-expiry tests. |
| SYS-086 | Accepted | Every provisioning operation must have authenticated versioned intent binding operation type, machine record and inventory revision, installer policy, platform and target-disk constraints, installable deployment scope, preservation policy, required authority ceremonies, enrollment authorization, network policy, validity, evidence, completion, and abort behavior; bootstrap hints may only locate candidate intent. | Missing, expired, substituted, wrong-record, wrong-platform, wrong-disk, over-scoped, unauthorized-network, and hostile-bootstrap intent tests. |
| SYS-087 | Accepted | Before any storage or firmware mutation, provisioning must resolve and present the exact target and topology, proposed create/replace/erase/preserve actions, capacity and reserve, backup/restore evidence, compromise policy, and irreversible boundaries and obtain operation- and target-bound confirmation; generic confirmation or authenticated intent must not make ambiguous target selection safe. | Similar-disk, enumeration-change, remapping, stale-plan, wrong-size, insufficient-capacity, missing-backup, compromised-state, cancellation, and confirmation-substitution tests. |
| SYS-088 | Accepted | The exact installer artifact and tool closure must be authenticated and reported and must carry no long-lived release, recovery, enrollment, platform-owner, or data-recovery private authority; booting it must not itself authorize state decryption, trust enrollment, machine binding, or normal release use. | Installer substitution, tool mutation, embedded-key inventory, unauthorized decrypt/enroll/bind/sign attempts, compromised-media, and owner-verification tests. |
| SYS-089 | Accepted | Provisioning must persist an attributable phase and every completed irreversible action, and after interruption each action must be proven idempotent, safely reversed, or resumed only through deliberate restart or recovery; partial storage, platform, identity, approval, or completion state must never become a normal enrolled machine. | Power loss and retry before/after partition, format, population, encryption, boot entry, identity, approval, trial, and completion boundaries. |
| SYS-090 | Accepted | Installation must consume a previously built, qualified, and authorized deployment set, verify the final target bytes and complete deployment closure, and make the final boot-selection entry point visible last; it must not resolve packages, rebuild artifacts, or render ordinary role configuration on the target. | Literal-source/target comparison, missing/substituted root/Verity/UKI/config/recovery member, package/network injection, hybrid entry, and finalization interruption tests. |
| SYS-091 | Accepted | Platform trust, data unlock and recovery, machine enrollment, normal release authorization, and recovery activation must retain separate accepted authorities, confirmations, evidence, loss behavior, and return paths even when coordinated in one provisioning session; no shared token, seed, credential, or confirmation may silently grant more than its named authority. | Cross-authority substitution, shared-credential abuse, platform reset, unlock loss, enrollment loss, signer compromise, recovery abuse, and add-test-remove ceremony tests. |
| SYS-092 | Accepted | Each machine identity must use a freshly and locally generated key with proof of possession and explicit exportability, hardware or vTPM protection, attestation, custody, rotation, loss, clone, replacement, and destruction semantics; machine name, SMBIOS, serial, MAC, TPM observation, hostname, and `/etc/machine-id` must not substitute for the enrollment identity or imply stronger assurance. | Key substitution/export, TPM/vTPM/software-key, copied disk/VM, duplicate-use, TPM clear, board replacement, machine-id restore, rotation, loss, and destruction tests. |
| SYS-093 | Accepted | First enrollment must use an authority-effectively single-use, short-lived voucher scoped to one operation and machine record, and approval must bind one exact fresh request, public key and proof, nonce, record, and identity epoch after independent confirmation; request races, duplicates, expiry, rejection, revocation, and re-enrollment must remain explicit rather than following first-writer-wins. | Stolen/replayed/expired voucher, two-request race, wrong-record/key/proof/nonce, installer-display substitution, duplicate approval, revocation, and new-epoch tests. |
| SYS-094 | Accepted | Every provisioning input or transport—including seed media, metadata, SMBIOS, fw_cfg, kernel arguments, remote URLs, Ignition, cloud-init, and installer credentials—must define authentication, scope, sensitivity, retention, deletion, completion, and replay behavior, and its reappearance or changed instance identity after completion must not rerun destructive work or change role, machine identity, preserved state, or selected deployment. | Input reattachment, metadata change, instance-ID change, cache loss, ordinary reboot, secret remanence, URL substitution, per-boot module, and explicit reprovision tests. |

## Interpretation of SYS-014 through SYS-018

`Bounded declarative data` means an operator-facing format without user-defined
functions, arbitrary evaluation, or a programmable module system. References,
explicit overlays, and conditional behavior supplied by separately owned and
tested tooling are not prohibited.

An upstream-native or pass-through path is not an uncontrolled bypass. It must
identify its owner and consuming component, participate in deterministic
composition, and remain subject to policy, validation where available, and
role qualification.

SYS-017 does not require secrets, enrollment records, or hardware-derived
values to be embedded in a release artifact. Late-bound inputs may be supplied
through a separately defined and qualified contract; they must not cause the
machine to build or evaluate a different OS release.
